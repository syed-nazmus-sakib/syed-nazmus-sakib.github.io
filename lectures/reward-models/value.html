Reward Models · Chapter 07

The value model: future success of a prefix

Abstract. A process reward model asks whether the latest reasoning step is correct. A value model asks something else: given everything written so far, how likely is the solver to reach a correct final answer? This chapter defines the value model as a probability of eventual success, shows why a correct step can still lead to a poor position, builds training targets from Monte-Carlo rollouts, connects the idea to value functions in reinforcement learning, and uses the model to steer search.

1. A different question

A PRM judges the step. A value model judges the position the step leaves you in.

In Chapter 06 the process reward model scored each step \(s_t\) by asking whether it is correct given what came before. That is a local question. When we use a model to guide generation, the question we really care about is global: if we continue from here, will we finish correctly?

A value model answers that global question directly. It looks at a reasoning prefix and returns a number between 0 and 1, read as the chance that a continuation from this prefix ends in a correct answer.

2. Definition

Write the problem as \(x\) and the first \(t\) reasoning steps as \(s_1,\ldots,s_t\). The prefix, or reasoning state, is

(1) \[ z_t=(x,s_1,\ldots,s_t). \]
Definition 7.1 · Value model

A value model is a function \(V_\theta(z_t)\in[0,1]\) trained to approximate

\[ V(z_t)=P\big(\text{eventual success}\mid z_t\big). \]

Architecturally it is the same Transformer-plus-head as earlier chapters. The backbone reads the prefix, we take the hidden state at the last token, and a linear head followed by a sigmoid turns it into a probability:

(2) \[ V_\theta(z_t)=\sigma\big(w^\top h_t+b\big),\qquad h_t=f_\theta(z_t)_{\text{last}}. \]

Nothing in the architecture says "value." The meaning comes entirely from the training target, which is the subject of Section 5.

3. Value model vs PRM

Process reward model

\(P(s_t\text{ correct}\mid x,s_{<t})\). Looks backward at the step just taken.

Was this step good?

Value model

\(P(\text{final success}\mid x,s_{\le t})\). Looks forward from the state the step creates.

Are we now in a good position?

The two often agree. A wrong step usually makes success unlikely, so both scores drop together. They come apart in two places: a correct step that leads somewhere hard, and a slightly sloppy step from which recovery is still easy.

4. Correct is not the same as promising

Problem: find \(23\times 17\). Two candidate first steps are generated.

Branch A. Split the multiplier:

(3) \[ 23\times 17=23\,(10+7)=230+161. \]

Branch B. "Add 23 to itself seventeen times." This is also mathematically valid.

A step-level PRM checks local correctness, so both steps score high:

(4) \[ q_A\approx 0.95,\qquad q_B\approx 0.95. \]

A value model asks how often each branch actually finishes correctly. Branch B needs sixteen additions, and every one is a chance to slip, so its value is lower:

(5) \[ V_A\approx 0.95,\qquad V_B\approx 0.55. \]
Remark · The slogan of this chapter

A correct step is not the same as a good future state.

5. Where the labels come from: rollouts

No human can label "probability of eventual success" directly. We estimate it by simulation. From the prefix \(z_t\), sample \(M\) full continuations with a completion policy \(\pi\), check each final answer, and record

(6) \[ R_m=\begin{cases}1 & \text{continuation } m \text{ ends correct}\\ 0 & \text{otherwise}\end{cases}, \qquad \hat V(z_t)=\frac{1}{M}\sum_{m=1}^{M}R_m . \]

With \(M=5\) and outcomes \([1,1,0,1,0]\), the estimate is \(\hat V=\tfrac{3}{5}=0.6\). Correctness only has to be checkable at the end (an answer key, a unit test, a proof checker), which is far cheaper than labelling every step by hand.

The estimate is noisy. Each \(R_m\) is a Bernoulli draw with mean \(V\), so

(7) \[ \operatorname{SE}\big(\hat V\big)=\sqrt{\frac{V(1-V)}{M}} . \]

At \(V=0.6\) and \(M=5\) the standard error is about \(0.22\): the label could easily have come out as 0.4 or 0.8. Quadrupling \(M\) only halves the error. Rollout budget is the main cost of value labels.

6. Training

Collect many prefixes (every step boundary of many sampled solutions), attach a rollout estimate to each, and regress:

(8) \[ \mathcal L_{\text{MSE}}=\big(V_\theta(z_t)-\hat V(z_t)\big)^2 . \]

Because \(\hat V\) is a probability, binary cross-entropy with a soft target is an equally natural choice, and it keeps gradients informative near 0 and 1:

(9) \[ \mathcal L_{\text{BCE}}=-\Big[\hat V\log V_\theta+(1-\hat V)\log\big(1-V_\theta\big)\Big]. \]
Note · Outcome labels are enough

A cheaper variant skips the extra rollouts. Take full solutions whose final answer is known to be right or wrong, and label every prefix of a solution with that solution's outcome. Averaged over many solutions, the expected label at a prefix is still its success probability. This is the idea behind outcome-supervised value models.

7. Link to RL value functions

Treat reasoning as an episodic MDP: the state is the prefix \(z_t\), an action appends a step, and the only reward is 1 at the end if the answer is correct. With no discounting, the state-value function of the completion policy \(\pi\) is

(10) \[ V^{\pi}(z_t)=\mathbb E_{\pi}\big[R\mid z_t\big]=P_{\pi}\big(\text{success}\mid z_t\big). \]

So the value model is exactly \(V^\pi\) from the value functions chapter of the RL notes, and the rollout estimate of Section 5 is Monte-Carlo policy evaluation. Two consequences follow.

  • Values depend on the policy. A strong solver and a weak solver assign different values to the same prefix. A value model is always the value under some completion policy, usually the model being trained.
  • Bootstrapping is possible. Instead of full rollouts, train toward the next state's prediction, \(V(z_t)\leftarrow V(z_{t+1})\), as in TD learning. This is cheaper but inherits TD's bias.

8. Value-guided search

The main use of a value model is deciding which partial solutions to keep exploring. Suppose the solver proposes three next steps and the value model scores the resulting prefixes:

(11) \[ V_A=0.92,\qquad V_B=0.31,\qquad V_C=0.78 . \]

With a beam of width 2 we continue A and C and prune B. Repeating this at every step is value-guided beam search. The same scores can serve as leaf evaluations in tree search such as MCTS, where they replace expensive full rollouts.

1 · Take the problem and the current prefixes.
↓
2 · Generate several candidate next steps for each prefix.
↓
3 · Score every extended prefix with \(V_\theta\).
↓
4 · Keep the top-\(k\) prefixes, drop the rest.
↓
5 · Repeat until prefixes reach final answers; return the best.

9. Progress as a step reward

A value model also gives a principled per-step reward. The step \(s_t\) moved us from \(z_{t-1}\) to \(z_t\); how much did it help?

(12) \[ A_t=V(z_t)-V(z_{t-1}). \]

This is an advantage in the RL sense. A step that raises the chance of success earns a positive reward, a step that wastes effort earns about zero, and a step that damages the solution earns a negative one. Rewarding progress rather than raw correctness avoids paying the solver for correct but useless steps, like Branch B in Section 4.

Proposition 7.1 · Progress telescopes

Summed over a whole solution of \(T\) steps, \(\sum_{t=1}^{T}A_t=V(z_T)-V(z_0)\). Total progress equals final value minus starting value, so progress rewards cannot be farmed by adding steps.

10. Weaknesses

  • Rollout cost. Each label needs \(M\) full generations; good labels need large \(M\).
  • Noisy targets. With small \(M\), labels scatter widely around the true value (Equation 7).
  • Policy dependence. As the solver improves, old value labels go stale and must be refreshed.
  • Checkable answers only. Rollout labels need an automatic success test, which open-ended writing lacks.
  • Exploitable in search. Search pushes toward prefixes the value model overrates, so its errors are amplified, not averaged out.

12. Worked example, step by step

A solver is at prefix \(z_1\) with \(V(z_1)=0.50\). It proposes three next steps. Five rollouts from each extended prefix give the outcomes below. Choose two branches to keep and compute the progress reward of each.

  1. Outcomes: A gives \([1,1,1,1,0]\), B gives \([0,0,1,0,0]\), C gives \([1,0,1,1,1]\).
  2. Estimates: \(\hat V_A=\tfrac45=0.8\), \(\hat V_B=\tfrac15=0.2\), \(\hat V_C=\tfrac45=0.8\).
  3. Beam width 2: keep A and C, prune B.
  4. Progress rewards: \(A_A=0.8-0.5=+0.3\), \(A_B=0.2-0.5=-0.3\), \(A_C=0.8-0.5=+0.3\).
  5. Caution: with \(M=5\) the standard error at \(V=0.8\) is \(\sqrt{0.8\cdot0.2/5}\approx0.18\). A and C are indistinguishable; B is clearly worse.

13. What comes next

The value model completes the "what is judged" axis: whole answers (ORM), single steps (PRM), and future success of a prefix (value). The next chapters change a different axis, what the model outputs, starting with reward models that return several scores at once.

Key idea to remember

PRM: was this step good? Value model: are we now in a good position to eventually succeed?
